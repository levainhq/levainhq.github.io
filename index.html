Levain

Agents that answer to you.

Levain wraps Claude Code and Codex. Each permission prompt either one's hook receives goes into a single queue. A signed standing grant settles the routine, and in away mode the rest waits for your signed answer, at your desk or on your phone. Memory persists across sessions, in a store you own and can read from outside any session. And a directive before every prompt pushes back on the habits an agent's training rewards. Apache-2.0. Python 3.12 and up.

A message that says yes is never authority.

Only a signature from an enrolled key is. The queue checks each answer against a signed authority log before the hook delivers it, so an agent can't type approval on your behalf. In Claude Code, a click in the agent's own dialog still works as it always did, but it is the agent's answer, unsigned. For the routine case you sign a standing grant: one agent, exact tools, one workspace, thirty days at most. Shell commands and edits to the agent's own config and hooks are never answerable by a grant.

Your memory lives on your machine, in a store you own.

The store is a local SQLite file. levain serve, the live browser view of it, binds loopback only and serves its own UI from the package, so it renders offline with no CDN. Levain adds no vendor host and no account. The sovereign entity, which ships as is, runs on glm-5.2:cloud through Ollama Cloud by default, so its episode content leaves your machine unless you give it a plain local model name.

What's actually in the wheel

Three jobs, one install

I run 10 to 15 agents at a time, and the permission prompt was the first thing that broke. Babysit every prompt and the agents sit frozen at a dialog nobody's looking at. Skip permissions and the agent acts with your full authority while nothing checks it first. Levain does three things at once. They only work together.

It holds what the agent does to your authority

One consent queue for Claude Code and Codex, kept in your Levain home. Each permission prompt either agent's hook receives is filed there. A signed standing grant settles the routine. In away mode, everything a grant doesn't cover waits for your signed decision. Desk or phone.

consent · grants · away mode · receipts

It lets the agent become someone

Memory that persists across sessions: episodes, a rolling summary your partner reads to orient each conversation, and patterns that carry the episodes they rest on as cited evidence. The seed gives the agent facts and a method, never a personality. It grows its own shape from what it lives. Two people who install Levain shouldn't end up with the same partner.

episodes · wrap · crystallized patterns · open loops

It works on how the agent behaves

The seed and a short posture file sit at the start of the context, and a hook adds one of several differently-worded directives before every prompt, so the pressure lands at both ends. When you correct a drift, that becomes an episode, and over time those episodes become the agent's own calibration.

activation · posture · directives · calibration

Look at it, and answer from anywhere

The cockpit, the phone and the coordinator

Your partner's memory normally only exists inside a session. levain serve shows it from outside: memory health, crystallized patterns, open loops, your state line, and in the Decisions panel the consent requests waiting on you. It is read-only until you pass --write.

Answer from your phone. The phone reaches the cockpit only after you pair it with a short code, and a passkey (Face ID, Touch ID or a device PIN) signs the answer. Put an https proxy you trust in front of the cockpit; Tailscale works. Signing from the phone needs the cockpit started with --sign-host, and the README has the exact command.

levain cockpit pair --short · levain cockpit pair --list

When nobody answers. A hold on a gated call (an edit of agent config or hooks, or levain push) that ends with no signed answer does not reject the call. It is marked undecided, the agent is told the action was not taken and is still open, and you rule on it later.

levain consent rule · levain consent deliver

The coordinator. One session holds the coordinator role. Words you drop from the cockpit, the phone or the terminal wake it when nobody holds the role, and its replies show on the cockpit's Coordinator panel. Silence is not "heard": a drop from the cockpit or the phone with no reply after 10 minutes shows as unanswered.

levain drop · levain coord status · levain coord reply

A team's decisions, in git

One engineer's partner, then everyone's

On a team, the decisions that matter (the client said no, leave this module alone) live in one person's head. Then the next engineer's agent simplifies them away. levain team keeps git as the wire. Each decision is a signed, hash-chained entry on an orphan branch of the project's own repository, with the decider's own words verbatim. A Claude Code hook shows the agent a teammate's ruling at the edit it governs and stops it once, so it reads the words and the owner before it changes anything.

The limits are stated in the Levain README: signatures prove which key wrote each commit, not that your git host showed you every commit, and edits made through Bash are not intercepted.

levain team init · record decision · consolidate · levain team view

The sovereign entity

Ships as is, with no new features for 1.0

levain init --adapter openhands scaffolds something different from the hook-wired adapters: an entity that is its own partner, with its own identity and its own memory store, never a hook into your Claude Code or Codex session. It runs on an open model you choose. You talk to it as a REPL, hand it one task and read the exit code, or run it on a schedule as a governed seat.

A sandbox for a coding agent is normally a jail: deny by default, allow the workspace. The floor inverts it: allow by default, deny the crown jewels.

The entity works like any normal shell, and a small, explicit set of paths pinned by absolute path stays denied whatever the model is told: ~/.anneal-memory, sibling stores and your SSH key material. It is a floor, not a guarantee, and the source names the routes it has not closed yet.

Standard credential stores are denied in every drive unless the entity sets deny_standard_creds to false. Reading a file is not an action the gate would ever ask about, so the floor denies the read instead.

~/.config/gh · ~/.aws/credentials · ~/.netrc · the macOS Keychain

Every action a scheduled seat or a run --task entity takes that reaches outside itself halts before it runs, with exit code 4 and the log left for you to read. The gate reads the tool, never the model's opinion of itself.

efferent gate · a default, not a lock

Boundaries, kept honest

What it does not do

A floor that oversells itself is worse than no floor, because you plan around the coverage you think you have. These limits are recorded in the README and the source, not just here.

Levain confines no Claude Code or Codex session. For those agents it installs hooks and consent paths. A consent hook answers a permission prompt. It does not stop an agent running as your user from doing what your user can do outside that prompt.

stated in the README

Some paths are cooperative. levain push and levain publish ask you for exactly what they will send and wait for your signed answer. They are the path a cooperative agent takes, not a boundary: a plain git push in a shell is not gated.

levain push · levain publish pypi | npm

Signed answers to permission prompts need away mode. With it off, the hook asks only your grants, and with none matching, the agent's own dialog asks you, as it would without Levain, except that an edit of agent config or hooks no enrolled key can approve is refused outside the agent's default dialog modes. On a Mac, away mode turns on by itself after 10 minutes with no keyboard, mouse or trackpad input and when a key you enrolled could sign an answer (an install set up before that rule needs levain consent away auto first); elsewhere only your word turns it on.

levain consent away on | off | auto

Start Claude Code at the workspace root. When the workspace is nested inside a larger repository, is a linked worktree or submodule, or is not a git folder, the hooks live in .claude/settings.json, which Claude Code reads only from the folder a session starts in. A session started in a subfolder runs none of them: no consent queue, no gate, no memory hooks.

levain update moves a workspace to the local layout after git init

Harnesses: Claude Code and Codex CLI are hook-wired and go through the consent queue. OpenHands is hookless and ships as is. One adapter per install, so make separate installs if you need more than one. Codex fires the consent hook in interactive sessions, not in codex exec.

--adapter claude-code | codex | openhands

Codex hook reliability: recent Codex versions have a platform-level hook-trust gap no consumer can work around. levain verify-hooks proves your scripts fire correctly by invoking each one with the JSON a harness would send. Whether Codex itself invokes them at runtime is up to Codex.

verify-hooks · doctor --invoke

No security absolutes. The confinement floor is real and load-bearing, but it denies a fixed set of crown-jewel paths and known escape routes, not "everything dangerous." The efferent gate covers the rest, and it is a default: setting efferent_gate: "ungated" turns it off everywhere, scheduled seats included. In the interactive REPL the gate is off and you are the check.

stated in levain/firing/confinement.py

On macOS, other programs' environments are visible to the entity's shell. Any process can read the environment and command line of every other process running as the same user, and no sandbox rule changes that. sudo levain setup-isolation runs the entity's shell as its own user, which hides them.

setup-isolation · macOS and Linux

Platforms: the daemon and governed seats run on macOS (launchd) and Linux (systemd --user). Windows is planned, not shipped. The sandboxed shell needs sandbox-exec on macOS or bwrap on Linux. Where there is none, the entity gets the file editor and no shell, never an unconfined one. The Linux specifics, including the Ubuntu AppArmor fix, are in the README.

levain doctor says which floor is active

One seat at a time: a governed seat runs one entity on one schedule. Coordinating several seats as a fleet is not built yet.

stated in the Levain README

Install

Two commands to a working partner

pip install levain
levain init --path ./my-partner

That creates the directory, runs the interview, lays down the seed, registers the adapter you choose, initializes the store at .levain/memory.db, and records the exact version set it composed. The consent hook is on by default for both adapters. Then open that directory with Claude Code or Codex and start working. 

levain init --web                    # browser form instead of the terminal interview
levain doctor                        # loud, in-environment health check
levain update                        # reconcile the whole stack to known-good
levain consent pending               # what's waiting on you
levain serve                         # live loopback view of your substrate
levain serve --write                 # ...and steer it, through the governed path

Levain composes a stack across two version lines that pip alone can't keep aligned: the library, versioned on PyPI, and your methodology seed, versioned inside Levain. pip keeps the library compatible but is blind to methodology drift. A new memory feature can land as a contradiction with your older, hand-tuned instructions instead of a clean addition. That drift is what breaks a long-running install, so doctor and update exist to hold the set together.

Build on it

One published seam

Writing your own surface over the substrate? levain.kernel is the published seam: the data model, the terminal and web drivers, and the governed write and action dispatch. Import one namespace instead of reaching into internals. Register extra read-only panels or extra governed verbs and they ride the same auth, confirm and audit envelope as the built-in edits. It's a pure re-export, and the governance lives in the substrate, not the surface.

14 exported names · levain.kernel

The division of labour with the substrate is the whole idea: anneal-memory is the memory; Levain is the symbiont that grows from it and governs every write into it. anneal-memory deliberately can't reach into your session. A memory library that hooked every prompt would forfeit the neutrality that lets it run under any harness. So on its own it gives you the stores and manual recall, and Levain wires the hooks that surface the right memory automatically. Levain depends on anneal-memory, never the reverse, and both are on PyPI.

Toward 1.0

Future tense on purpose

Everything above is installable today. This section is future tense because none of it is released. 1.0 is a finish, not a freeze: I want what you read here to be a truthful account of what Levain is, not a pile of pieces that don't cohere yet. It stays open source.

One cockpit, desktop and phone. The cockpit becomes the one responsive surface for both, and its design is a release criterion.

Who it's for

Operator-class developers: the people who run coding agents for real, feel session amnesia as a real problem, and would otherwise build their own fix. If you've written your own substrate-management scripts, you'll recognize the pieces. If continuity file and session-closing reflection don't land yet, this probably isn't your tool yet. Levain is a cognitive symbiont: governance built in from the ground up for a real augmented partnership with your AI, not another software factory with a gate bolted on.
